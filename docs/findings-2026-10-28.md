# First speed runs on a V100, 28 Oct 2026

This note reports what the first three vLLM runs showed and what they do not show. The numbers are **measured by Starfield**. The method is in [the methodology page](methodology.md). The raw files are in [`results/`](../results/).

## Setup

| Item | Value |
|---|---|
| GPU | Tesla V100-SXM3-32GB, one card, 32 GB, compute capability 7.0 |
| Driver | 580.178.04 (CUDA 13.0 supported), engine built for CUDA 12.8 |
| Engine | vLLM 0.19.1, torch 2.10.0, transformers 4.57.6 |
| Precision | fp16 |
| Prompts | `model-watch-prompts-v1`, 150 prompts, hash `44ff438e...db8a` |
| Load | 8 requests at once, output capped at 256 tokens, greedy, seed 0 |
| Repeats | 3, each with a fresh server and prefix caching off |
| Context limit | 4096 tokens for every model |
| Thinking | Off for Qwen3-8B and granite-4.2-8b. Olmo-3 has no thinking mode. |

All 450 requests per model completed. None failed.

## How to read these numbers

- This is not a ranking. It is three models, one GPU, one engine and one load of 8 requests at once.
- The models stop at different lengths. Granite wrote 27,622 tokens for the same 150 prompts, and Qwen3-8B wrote about 21,586. A model that writes more has more to generate, so compare token counts before comparing speeds.
- The first Olmo-3 repeat was slower to start (264.9 ms to first token, against 182.8 and 183.2). We did not find the cause. The mean time to first token for Olmo-3 is pulled up by that one repeat.
- Greedy decoding is not exact when 8 requests run at once. Qwen3-8B wrote 26 more tokens in repeat 3 than in the other two.
- The vLLM tool counts input tokens from the raw prompt, without the chat template. We do not use its input-token total or its "total tokens per second" column.
- Speed says nothing about answer quality. No quality check has run.

## What we found about the method

- Olmo-3 does not load with transformers 5.x at vLLM 0.19.1 (`KeyError: 'rope_theta'`). All three runs use transformers 4.57.6 so they are comparable.
- Granite fails on memory at its default 131072-token context. Every model now runs with `--max-model-len 4096`. The longest prompt plus 256 output tokens is about 1,300 tokens, so no prompt is cut.
- On a V100, vLLM falls back to the `TRITON_ATTN` backend, because FlashAttention 2 needs compute capability 8 or higher. The "FA2 not supported" log line is expected.
- The machine has several GPUs, and the first record listed all of them. The run now sets `CUDA_VISIBLE_DEVICES` and the record lists only the card used.

## What has not been run

- vLLM v0.32.0 on an A100. The prefix-caching flag at that version is unchecked.
- llama.cpp. The host has no CUDA compiler, so `llama-bench` needs a prebuilt CUDA binary. GGUF conversion and flash attention on the V100 are unchecked.
- Quality checks, energy and cost per million tokens.

A mistake in any number here goes in the [corrections log](../CORRECTIONS.md).
